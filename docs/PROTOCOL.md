# VOROTEX K13 (USB 30FA:2350): протокол конфигурирования, результаты статического анализа

Что разбиралось: `VOROTEX-K13.exe` (MFC, x86, 4 МБ; radare2 + Ghidra 12.2 headless, декомпиляция в `/workspace/gh/out1.c`, `/workspace/gh/out2.c`), ini‑файлы из `config/` и `skins/*`, открытый проект того же производителя (`zergzorg/vorotex-k08-mac`, склонирован в `/workspace/vorotex/ref-k08`).

Уровни уверенности: **[ПОДТВ]** — видно прямо в коде или совпадает с независимым источником; **[ВЕР]** — вероятно, по косвенным признакам; **[ГИП]** — гипотеза, проверить на устройстве.

---

## 0. Кратко

* Чип: **Instant Microelectronics (VID 0x30FA)**, в `config.ini` указано `KB_NAME=IST83025B-K210`, `KBCOMPANY_NAME=SHI XING SHENG` (东莞市世兴盛 = MKESPN/VOROTEX). Это обычный «клавиатурный» контроллер с матрицей **8×20 = 160 позиций**, в K13 из неё задействована одна строка. **[ПОДТВ]**
* Транспорт: **только HID Feature‑репорты**, `HidD_SetFeature` / `HidD_GetFeature`, **Report ID = 0x07**, длина 8 байт (ID + 7 байт данных). `WriteFile`/`ReadFile`/`SetOutputReport` для конфигурации не используются. **[ПОДТВ]**
* Модель такая: **приложение пишет образ настроек в EEPROM/flash устройства побайтово** (команда `0x18`: «положить байт в буфер», «записать буфер по адресу», «прочитать байт»). Отдельных команд вида «назначь клавишу» или «включи режим подсветки» нет: всё это поля в образе памяти. **[ПОДТВ]**
* Тот же протокол (`07 18 03/05/09…`, `07 20`, `07 10`) независимо разобран и работает в `vorotex-k08-mac` для VOROTEX K08 (30FA:1340). Протокол **подтверждён двумя источниками**, а **раскладка памяти у K13 другая** (другая прошивка). **[ПОДТВ]**
* **Профили в родном приложении есть только на стороне ПК.** Config1..5 лежат в `config.ini`, а при «Применить» в устройство заново записывается весь образ (так и работал удалённый `CycleVorotexProfile.cs`). Аппаратного переключения профилей в коде под K13 не найдено. **[ВЕР]**

## 1. Как найти устройство и какой интерфейс открывать

Из `FUN_004076a0` **[ПОДТВ]**:

1. `HidD_GetHidGuid` → `SetupDiGetClassDevs(DIGCF_PRESENT|DIGCF_DEVICEINTERFACE)` → перебор `SetupDiEnumDeviceInterfaces` (до 128).
2. Для каждого: `CreateFile(path, 0, FILE_SHARE_READ|WRITE, OPEN_EXISTING)` → `HidD_GetAttributes`.
   Подходят: **VID 0x30FA, PID 0x2350** (основной) **или** VID 0x2130 / PID 0x30FA (запасная пара, похоже на опечатку или другую ревизию).
3. `HidD_GetPreparsedData` + `HidP_GetCaps`, выбор по `UsagePage/Usage` коллекции:
   * **UsagePage 0xFF01, Usage 0x01** → `CreateFile(GENERIC_WRITE)` → **рабочий хэндл**. Через него идут **все** SetFeature/GetFeature. Длина репорта берётся из `Caps.FeatureReportByteLength`.
   * **UsagePage 0xFF00, Usage 0x01** → `CreateFile(GENERIC_READ)` → второй хэндл. Для конфигурации не используется (видимо, для входных репортов или уведомлений).
   * В Windows это и есть две vendor‑коллекции `MI_01&COL06/COL07`. Какая из них FF00, а какая FF01, надо проверить: смотреть `HidP_GetCaps` или дамп дескриптора.
4. `RegisterDeviceNotification` для отслеживания подключения и отключения.

> Для своего софта: открывать коллекцию **MI_01, UsagePage 0xFF01 / Usage 1**. Доступ на запись к vendor‑коллекциям Windows даёт без прав администратора.

Особенность **[ГИП]**: местами приложение вызывает `HidD_GetFeature` с длиной 0x10, 0x12 и 0x15 и читает байты 14, 15 и 20 ответа. Значит, у Feature‑репорта 7 в коллекции FF01 длина может быть больше 8 (а у K08 ровно 8). Нужен дамп HID‑дескриптора.

## 2. Формат репорта

```
byte0  = 0x07                 Report ID
byte1  = команда              0x18 (память), 0x09 (режим клавиатуры), 0x20 (выход/применить), 0x10 (функция, из K08)
byte2..7 = параметры
```

Контрольной суммы нет. **[ПОДТВ]**

### 2.1 Команда 0x18: доступ к памяти **[ПОДТВ]**

`byte2` — битовые флаги. Генерирует их `FUN_00413090` как `b5<<5 | b4<<4 | b3<<3 | b2<<2 | b1<<1 | b0`. Встречаются значения:

| byte2 | Смысл | Полный пакет |
|---|---|---|
| `0x03` | положить байт в буфер (index `i`) | `07 18 03 i  AL AH  DATA  N-1` |
| `0x09` | записать буфер из N байт по адресу | `07 18 09 00 AL AH  00  N-1` |
| `0x05` | запросить байт i по адресу; ответ в `GetFeature` byte1 | `07 18 05 i  AL AH  00  N-1` |
| `0x01` | конец операции / освобождение | `07 18 01 00 AL AH 00 00` |
| `0x00` | сброс / idle | `07 18 00 00 00 00 00 00` |
| `0x11` | «завершить загрузку» (в конце записи и при подключении) | `07 18 11 00 00 00 00 00` (или `…60` в режиме big) |
| `0x81` | стирание страницы 32 Б (только в режиме big, у нас **выключен**) | `07 18 81 00 AL AH 00 60` |

`AL/AH` — адрес (little‑endian), `N` — длина блока (родное приложение пишет по ≤8 байт, K08‑тул по ≤32). В байте 7 биты 0x60 ставятся только при глобальном флаге `DAT_006412d4`. Этот флаг лежит в .bss и нигде не присваивается, поэтому для K13 **byte7 = N-1**.

**Запись блока** (`FUN_004071e0(addr, data, n)`):
```
for i in 0..n-1:  SetFeature(07 18 03 i AL AH data[i] n-1)
Sleep(2)
SetFeature(07 18 09 00 AL AH 00 n-1)
Sleep(10)
SetFeature(07 18 01 00 AL AH 00 00)
```
**Чтение блока** (`FUN_00406fe0`). Родное приложение делает лишнюю «пустую» загрузку буфера, K08‑тул обходится без неё:
```
for i in 0..n-1: SetFeature(07 18 05 i AL AH 00 n-1); Sleep(1..2); GetFeature(ID 7) → buf[1] = байт i
SetFeature(07 18 01 00 00 00 00 00)   (K08: 07 18 00 …)
```

### 2.2 Прочие команды
* `07 20 00 00 00 00 00 00` — шлётся при закрытии окна и выходе. В K08‑туле называется `commit`. Предположительно «выйти из режима конфигурирования, перезагрузить настройки». **[ПОДТВ отправку, ВЕР смысл]**
* `07 09 FL 00 00 00 00 00` — флаги режима клавиатуры. Перед загрузкой шлётся `07 09 41 …`, при захвате клавиши в окне «нажмите клавишу» `07 09 40 …`, после него восстанавливается битовая маска (`KEYSMODE`, Win‑lock, All‑key‑lock и т. п.). 0x40 скорее всего «не отдавать нажатия в систему». **[ВЕР]**
* `07 10 01 NN …` — «функциональный код» (в K08 переключает аппаратный профиль, текущий профиль читается из `GetFeature` byte6 bits2..3). В exe K13 **не встречается**. **[ГИП, проверить]**

### 2.3 Последовательность «Применить» (`FUN_0040fe10`) **[ПОДТВ]**
```
1. 07 09 41 00 00 00 00 00 ; Sleep 200
2. GetFeature(ID7, 16 байт) → BASE = b[14] | b[15]<<8      (адрес блока конфигурации)
3. write(0x00D0, E1 1E BASE_lo BASE_hi F0 0F 00 00)          (заголовок: магия 0x1EE1, указатель, 0x0FF0)
4. read(BASE, 1) — сохранить биты 5,4 первого байта
5. write(BASE+0x00 .. +0x17)  — глобальные флаги + цвета подсветки (3×8 байт)
6. write(BASE+0x18 .. +0x1F)  — режим подсветки + указатели на keymap и таблицу макросов
7. write(BASE+0x20, 1 байт)   — колесо (USCROLL0<<4 | USCROLL1)   [ВЕР]
8. write(BASE+0x48 .. +0xE7)  — раскладка, 160 байт
9. write(BASE+0xE8 .. +0xF3)  — Fn+F1..F12 (12 байт, для K13 не нужно) + 4 нуля
10. write(BASE+0xF8 ..)       — таблица 20 макросов × 5 байт (14×8 = 112 байт)
11. write(macro data)         — тела макросов, выравнивание по 8, лимит 0x4000
12. 07 18 11 00 00 00 00 00 ; Sleep 10 ; 07 18 00 00 00 00 00 00
```
Каждый байт — отдельный Feature‑репорт с паузами, поэтому полная запись занимает **секунды** (оценка 1–3 с). Писать имеет смысл только изменённые 8‑байтовые блоки.

При подключении (`FUN_00414370`): `07 18 11 …` → `Sleep 10` → `07 18 00 …` → `GetFeature(21 байт)` (byte20==2 → флаг, меняющий обработку скорости некоторых режимов) → `GetFeature(18 байт)` (byte2 bit0 → флаг).

## 3. Раскладка памяти конфигурации (смещения от BASE)

| Смещение | Размер | Содержимое | Уверенность |
|---|---|---|---|
| 0x00–0x17 | 24 | флаги (бит‑маска из 8 переключателей: KEYSMODE, Win‑lock, …), цвета LED. **Цвета по 4 бита на канал (0–15)**, по два значения в байте | структура [ПОДТВ], поля [ГИП] |
| 0x18 | 1 | `X<<6 \| react<<3 \| (Y&7)` (HR_DIRECTION / HR_SPEED / HR_BRIGHT?) | [ГИП] |
| 0x19 | 1 | `sym<<7 \| colorIndex<<4 \| (HR_LED_MODE & 0x0F)` | режим в младшем ниббле [ВЕР] |
| 0x1A | 1 | `0x80 \| маска 7 цветов цикла (RGB_HR_COLOR_EN0..6)` (или 0x7F в одноцветном режиме) | [ВЕР] |
| 0x1B | 1 | маска разрешённых режимов (HR_LED_MODE_EN) | [ГИП] |
| 0x1C–0x1D | 2 | указатель на keymap (= BASE+0x48) | [ПОДТВ] |
| 0x1E–0x1F | 2 | указатель на таблицу макросов (= BASE+0xF8) | [ПОДТВ] |
| 0x20 | 1 | колесо: `USCROLL0<<4 \| USCROLL1` | [ВЕР] |
| 0x48–0xE7 | 160 | **keymap**: 20 столбцов × 8 строк, **по столбцам**: `BASE+0x48 + col*8 + row` | [ПОДТВ] |
| 0xE8–0xF3 | 12 | коды Fn+F1..F12 (UFN_F*) | [ВЕР] |
| 0xF8–0x15B | 100 | 20 записей макросов по 5 байт | [ПОДТВ] |
| 0x160… | — | тела макросов | [ПОДТВ] |

Где лежит BASE, сообщает само устройство (GetFeature, байты 14–15), а адрес 0xD0 хранит заголовок `E1 1E BASE F0 0F`.

#### Заголовок 0xD0: что это за байты (v5.2, 14.11.2026)

* Родная программа **никогда не читает и не проверяет** 0xD0: в `FUN_0040fe10` при каждом «Применить» она записывает константу
  `mov word [ebp-0x18], 0x1EE1` (@0x4103eb, файл 0xF7F5) + BASE из GetFeature + `F0 0F 00 00` (`push 0xd0; call 0x4071e0`).
  Других вариантов константы в exe нет (поиск по шаблону `66 C7 45 xx ?? 1E … 68 D0 00 00 00` — один результат).
* Значит `E1 1E` — **метка «блок настроек записан программой»** (u16 LE 0x1EE1), а не контрольная сумма: от содержимого не зависит
  (во всех наших 18 дампах, до и после записей, — одинаковая `E1 1E E0 00 F0 0F 00 00`).
* На K13 производителя прочитано **`DA 1E`** (0x1EDA): **второй байт 0x1E совпадает, меняется первый**. Наиболее вероятно —
  ревизия программы/прошивки, которая записала блок (заводская утилита или другая сборка ПО). Чем именно является первый байт,
  без дампа их устройства подтвердить нельзя. **[ГИП]**
* `F0 0F` = 0x0FF0 — по всей видимости, размер/граница области (BASE + 0x0FF0 ≈ конец 4-КБ страницы). **[ГИП]**
* Вывод для записи: важна не метка, а **BASE и структура блока**. v5.2 проверяет: BASE в заголовке (или из GetFeature),
  хвост `F0 0F 00 00`, совпадение BASE заголовка и GetFeature, указатели BASE+0x1C = BASE+0x48 и BASE+0x1E = BASE+0xF8,
  ≥ 90 % понятных кодов в keymap, все 20 записей таблицы макросов начинаются с 0x07. Всё совпало, а метка `xx 1E` другая →
  запись разрешена («совместимо»), **метка устройства сохраняется** (не перезаписывается на E1 1E). Что-то не совпало →
  диалог с найденными байтами: «Продолжить запись» / «Отмена» (бэкап уже сделан, после записи — сверка и автоматический откат).

### 3.2 Джойстик (по запросу пользователя)

* **Цифровой, 4 направления.** Каждое направление — отдельный «ключ» матрицы (col 12–15), как обычная клавиша. Аналоговых данных нет: в дескрипторе нет gamepad или joystick‑коллекции, в коде нет осей, отдельной зоны мёртвого хода тоже. **[ВЕР]**
* **Каждое направление переназначается независимо** на любой код, как обычная клавиша: HID‑клавиша, медиа, LED‑функция, макрос, 0xFF «отключено». **[ПОДТВ]** У пользователя сейчас в Config1 и Config2 `KU_86/99/100/101 = 255`, то есть джойстик **отключён**.
* **Диагонали** у 4‑кнопочного джойстика — это одновременное замыкание двух направлений: прошивка просто пошлёт оба кода. Отдельного «слота» под диагональ в прошивке нет. **[ВЕР]** Отдельные действия на диагонали делаются на стороне ПК: назначить направлениям F13–F16 и распознавать аккорды (см. §6).
* **Нажатие джойстика.** В `KB.ini`/`KbIndexText.ini` UI‑индекса под него нет. Если физически оно есть, то это col 16 (0xF4) или col 17 (0xE9, переключение режима подсветки). Скорее всего, одно из них — нажатие колеса, другое — нажатие джойстика. Прошивка вряд ли запрещает писать в эти байты свой код: родное приложение их просто не показывает. **[ГИП — проверить первым делом]**
* «Касания» (touch) без нажатия у такой механики не поддерживаются: в коде и ini следов нет.

## 5. Макросы

* Индексная таблица по адресу BASE+0xF8, 20 записей × 5 байт **[ПОДТВ структура]**:
  `[0x07, (len & 0x7F) | (mode==2)<<7, addr_lo, ((mode==1)<<7 | flag<<6) | (addr_hi & 0x3F), len>>7]`
  Пустой слот: адрес предыдущего, длина 0.
* Тело макроса: 2 байта заголовка (число повторов lo/hi; в режимах 1/2 — `01 00`), дальше события по 2 байта `[delay | 0x80?, code]`. Задержка = мс/8, максимум 0x7F; длинные задержки разбиваются на дополнительные записи `7F`. Есть спец‑события 0xF6 (движение мыши XY, ещё +4 байта), 0xF7 (колесо мыши), 0xF8/0xF9 (LED/текст). Общий лимит памяти 0x4000. **[ВЕР/ГИП: проверять дампом]**
* Режимы повтора в UI: «N раз», «пока удерживается», «до повторного нажатия».
  В skin_mac.ini родной программы три переключателя: `SEL_TILL_RELEASE` (mode1, «пока удерживается»), `SEL_TILL_CILICK` (mode2, «до повторного нажатия») и `SEL_REPEAT_EN` + `REPEATTIMES` (N раз). Значит, toggle выполняет сама прошивка: бит 7 второго байта записи таблицы, тело начинается с `01 00`. mode1 подтверждён дампом; mode2 взят из декомпиляции и UI, дампом/на железе пока не проверен **[ВЕР]**. Остановит ли второе нажатие макрос сразу или после текущего прохода, решает прошивка (не проверено).
* Файлы `macro/*.dat` и `defMacro.dat` — двоичный формат родного приложения (структура ≈ 0xB90 байт на макрос: имя, массивы событий). Для своего приложения он не нужен.

## 7. Что проверить вживую (в порядке приоритета)

1. **Дамп HID‑дескриптора и Caps** коллекций COL06/COL07: какая FF00, какая FF01, `FeatureReportByteLength`, есть ли Report ID 7 и какой он длины. (Средства: `hidapitester`, USBView, наш мини‑скрипт `HidP_GetCaps`.)

3. **Диф‑эксперименты:** в родном приложении меняем по одному параметру (режим подсветки, яркость, скорость, цвет, направление, колесо, одну клавишу, один макрос), жмём «Применить» → снова дамп → diff. Так закроются все [ГИП] в §3–5. Параллельно можно снять USB‑трафик (USBPcap + Wireshark) при «Применить», чтобы увидеть точную последовательность.
4. **Col 16/17:** записать в BASE+0x48+16*8 и BASE+0x48+17*8 тестовые коды (например F13/F14), нажать колесо и джойстик и посмотреть, что придёт. Так определится, где нажатие джойстика и есть ли оно вообще.
5. **Колесо:** записать в BASE+0x20 значения ниббла 0..15 и проверить, принимает ли прошивка что‑то кроме 8 Roll‑функций.
6. Проверить, нужен ли `07 20` (или `07 18 11` + `07 18 00`), чтобы изменения применились без переподключения, и есть ли у K13 команда `07 10` (аппаратные профили, как у K08).
7. Перед любой записью — **полный бэкап** памяти (0x0000–0x3FFF), а после записи — проверка обратным чтением.

## 10. Живое устройство — подтверждено (12.11.2026, только чтение)

**Коллекции HID 30FA:2350** (MI_01): COL01 consumer RID1; COL02 system control RID2; COL03/04/05 клавиатура RID3/4/5 (диапазоны usage 0–0x2F / 0x30–0x67 / 0x68–0x9F); COL06 UP 0xFF00/U1, input RID6, 2 байта; **COL07 UP 0xFF01/U1, Feature RID7, FeatureReportByteLength=8** (value cap usage 0x20, 8 бит × 7); COL08 клавиатура RID8 (модификаторы + 0–0xE7); COL09 мышь RID9 (X/Y 16 бит, колесо, 5 кнопок). MI_00 — boot-клавиатура. ✅ Высокая уверенность.

**GetFeature(RID7)** принимает буфер длиннее 8 байт и отдаёт статус-блок:
`07 xx 41 C0 43 01 02 12 01 02 64 02 28 01 E0 00 D8 01 02 40 02 02 02 … 00 …`
- байт1 — последний прочитанный командой `07 18 05` байт (регистр ответа);
- байты 14–15 = **BASE = 0x00E0** ✅ (совпадает с заголовком);
- байт20 = 0x02 (значит флаг 627e24 = 0); байт2 = 0x41 (бит0=1; возможно текущие флаги режима, ср. `07 09 41`);
- байты 16–17 `D8 01` = 0x01D8 — гипотеза: конец данных/указатель (низкая уверенность).

**Важная поправка к §чтения:** `07 18 05 i AL AH 00 N-1` + GetFeature возвращает `buffer[i & 7]` — **адрес игнорируется**. Это чтение 8-байтного RAM-буфера передачи, а не флеша. Проверено: адреса 0x0000–0x01FF, 0x0148, 0x1234, N до 64 → всегда `E1 1E E0 00 F0 0F 00 00` (буфер сейчас содержит заголовок 0xD0). Значит, для чтения памяти обязательна команда загрузки страницы `07 18 00 00 AL AH 00 00` (как в fcn.00406fe0), до неё вендор заливает буфер нулями через `07 18 03`, после — `07 18 01`. Эти команды пока не отправлялись (запрещены текущими правилами).

**Обновление (вариант (a) одобрен и проверен):** `07 18 00 00 AL AH 00 00` (загрузить 8-байтовый блок по адресу в буфер) → `07 18 05 i …` + GetFeature (i=0..7) → `07 18 01 00 00 00 00 00` (конец) — **рабочее чтение памяти** ✅. Команды 03/09/11/07 09 не нужны и не отправлялись. Пробное чтение 0xD0 вернуло заголовок, статус-блок не изменился (кроме байта1), все 10 HID-интерфейсов на месте. Полный дамп 0x0000–0x07FF ×2 прохода — 0 расхождений (~72 с, ~35 мс/байт); 0x0800–0x0FFF — сплошь FF.

## 13. Трейлер 0x023C–0x023F и точная последовательность «Применить» (из кода, `FUN_0040fe10` / `FUN_004071e0`)

### 13.1 Трейлер — НЕ контрольная сумма ✅
Таблица макросов собирается в стековом буфере **100 байт** (`[ebp-0x84]`), а пишется **14 блоками × 8 = 112 байт** (цикл с `0xE` @0x41174d). Это переполнение буфера в вендорском коде. Байты 100..111 таблицы — соседние переменные стека:
* байт 100 (= **BASE+0x15C = 0x023C**) — буфер `[ebp-0x20]`, куда до этого считали **1 байт BASE+0** (`FUN_00406fe0(BASE, buf, 1)` @0x4108da) → всегда равен BASE[0] (`C0`). Проверено на всех трёх дампах.
* байты 101..103 (0x023D–0x023F) — **неинициализированный стек** (в коде нет ни одной записи в `[ebp-0x20]`, кроме этого чтения) → случайные значения при каждом «Применить»: `FA ED 00`, `FC 1C 05`, `FD A1 00`.
* байты 104..111 (0x0240–0x0247) — тоже мусор стека, обычно сразу перезаписывается телом первого макроса (тела начинаются с `align8(BASE+0xF8+100)` = 0x0240).
* Прошивка эти байты, очевидно, не проверяет (устройство работает при любых значениях). **Нашему приложению:** писать таблицу ровно 100 байт (+ при желании 0x023C = BASE[0], 0x023D–0x023F = 00), ничего не вычислять.

### 13.2 Примитив записи `FUN_004071e0(addr, data, n)` (n ≤ 8)
```
for i in 0..n-1:  07 18 03 i AL AH data[i] n-1        ; в буфер (нет пауз между байтами)
Sleep 2
07 18 09 00 AL AH 00 n-1                               ; commit буфера по адресу
Sleep 10
07 18 01 00 AL AH 00 00                                ; конец
```
(если флаг `DAT_006412d4`≠0, байт 7 = n+0x5F вместо n-1 и при Apply сначала стирание `07 18 81 00 lo hi 00 60` по 0x20 байт для 0..0x3E0. В exe не найдено ни одной прямой записи в этот флаг → для K13 = 0, стирания нет.)

### 13.3 Последовательность «Применить» (полная)
1. `07 09 41 00 00 00 00 00`, Sleep 200.
2. GetFeature(16) → BASE (байты 14–15).
3. write(0x00D0, `E1 1E BASE_lo BASE_hi F0 0F 00 00`).
4. read 1 байт BASE+0 (сохраняются его биты 5,4).
5. write(BASE+0x00, 8): `[flags, C1a, C1b, C2a, C2b, C3a, C3b, C4a]`, flags = b7 DAT_622104(=1) b6 641304 b5,b4 (сохранены с устройства) b3 641310 b2 641314 b1 641318 b0 64131c. Цвет = `R<<4|G`, `(X<<4)|B`; X-нибблы в +2/+4/+6 — индексы первых включённых элементов трёх 12-битных масок, в +8/+0xA/+0xC — старшие 4 бита этих масок.
6. write(BASE+0x08, 8), write(BASE+0x10, 8) — остальные цвета/маски/параметры LED.
7. write(BASE+0x18, 8): режим LED + указатели keymap (BASE+0x48) и таблицы макросов (BASE+0xF8).
8. write(BASE+0x20, **1 байт**): колесо. **BASE+0x21..0x47 приложение не пишет никогда** (там заводское/старое содержимое — не трогать).
9. write keymap: 20 блоков × 8 (BASE+0x48..0xE7), **всегда целиком**.
10. write(BASE+0xE8, 8) Fn+F1..F8; write(BASE+0xF0, 8) = Fn+F9..F12 + `00 00 00 00`.
11. write таблицы макросов: 14 × 8 с BASE+0xF8 (100 байт + 12 байт мусора, см. 13.1).
12. Для каждого используемого макроса (коды A5..AF/B8..C0 в keymap): тело блоками по 8, последний — частичный (n = len & 7); проверка лимита `addr+len < MEMSIZE-0x48` (MEMSIZE из байта 0x627e3a: 0x1FF/0x3FF/0x7FF/0xFFF/0x1FFF/0x3FFF) и ≤ 0x4000.
13. `07 18 11 00 00 00 00 00`, Sleep 10, `07 18 00 00 00 00 00 00`.

Итого: **приложение переписывает всю конфигурацию при каждом Apply** (≈ 60 блоков × ~12 мс + паузы), заголовок тоже; хвост старых макросов не стирается. Повторить в своём ПО безопасно можно ровно этой последовательностью; для частичных правок достаточно переписать изменённые 8-байтовые блоки (кроме п.1/13 — их порядок сохранить).
